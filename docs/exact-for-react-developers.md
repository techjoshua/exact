# eXact for React developers

This guide maps everyday React component work to native eXact authoring. The two frameworks share
TypeScript and JSX surface syntax, but they do not share a runtime architecture. A React function
component executes again to describe its next interface; Hooks preserve state and effects across
those executions, and React reconciles the resulting tree. An eXact component is a durable,
inspectable instance generated by the compiler. The authored component supplies state defaults,
reactive relationships, tasks, lifecycle intent, and a view description to compiler analysis. The
authored function neither executes as a setup callback nor reruns to produce updates; the generated
reactive state machine owns runtime behavior.

The public side-by-side examples live in the docs application at `#/react-developers`. This
reference records the authoring rules behind those comparisons.

## Everyday mappings

| React pattern                                        | Native eXact pattern                                                                                                                                                  |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `useState()`                                         | Initialize and mutate fields on `this.state`.                                                                                                                         |
| Derived values calculated during render              | Write ordinary state-dependent constants in component setup; the compiler makes safe expressions reactive and shared.                                                 |
| `prop={prop}`                                        | Use the ordinary form or pun a matching variable name as `<Avatar {user} />`.                                                                                         |
| Parent-owned objects passed as props                 | Read them directly as reactive, readonly inputs, including nested plain objects and collections; report child edits through an authored callback.                     |
| Conditional class strings                            | Use ordinary `className`, array/object class composition, or `className:token` for one statically known conditional token.                                            |
| Controlled input value plus assignment handler       | Use a finite `property:event` binding such as `value:onInput`, `checked:onChange`, or `open:onToggle`.                                                                |
| Immutable collection replacement to expose an update | Mutate observable state objects, arrays, `Map`, or `Set` directly.                                                                                                    |
| JSX `key` on every list use                          | Declare an `@exact key` field on the item type, use a conventional JSX `key`, or call `this.map()` with an explicit selector.                                         |
| `useEffect()` for coordinated async work             | Define and activate an ordinary function task; add `TaskContext` only for explicit placement, concurrency, readiness, priority, optimism, or generation capabilities. |
| `useEffect()` cleanup for a mounted resource         | Create recognized resources in setup and let the compiler inject ownership and cancellation; use lifecycle registration when its timing matters.                      |

Compiler-owned `property:event` bindings require a compiler-proven writable location, normally a
field on `this.state`. Reactive props update their consumers when the parent changes them, but they
remain readonly to the receiving component and therefore cannot be used as the writable target of
binding shorthand.

## Client and server composition

React Server Components and eXact continuations solve overlapping problems with different
architectures. React Server Components execute only on the server and send a serialized component
model to React on the client. Interactive state and event handlers belong in an explicitly marked
Client Component. Mutations use framework-integrated Server Functions or another application
transport, and a framework may rerun affected Server Components and merge a new RSC payload after
the mutation. React defines the component protocol; routing, dispatch, invalidation, and deployment
belong to an RSC-enabled framework such as Next.js.

eXact retains one native component model. The compiler partitions server-dependent task segments
from the browser-owned durable component instance and generates the allowlisted operation,
transport-safe input record, cancellation path, result validation, and state publication. Blocking
server continuations settle during SSR; hydration restores their settled public state without
repeating the query. Later browser interactions can run synchronous optimistic state before their
server continuation, then publish validated authoritative effects into the same state machine.

For a browser interaction, both architectures serialize framework-selected operation identity and
public inputs, send a request to an application endpoint, execute authorized server work, and
return serializable output. Neither eliminates the network boundary. They differ in the authored
unit and the response's place in that unit. eXact keeps the native components in one
compiler-analyzed graph, resumes an allowlisted server-dependent continuation, and reconnects its
validated effects to browser-owned component state. In the Next.js example, server rendering,
client interactivity, and mutation are authored as Server Components, a Client Component, and a
Server Function; revalidation reruns affected Server Components and merges their RSC payload.

The public guide's multi-file product example compares this lifecycle directly:

1. Both sides define the same `Product` model and `ProductRepository` API. eXact resolves its
   implementation from request-scoped server context; the React example exports its implementation
   from a `server-only` module.
2. Each `Recommendations` component resolves or imports that server repository itself. Its parent
   passes only `category`, not fetched recommendations or data-access plumbing.
3. eXact renders the save control as an ordinary native component. The compiler places only its
   server task continuation. React crosses an explicit `'use client'` module boundary for the
   interactive control.
4. eXact task policy owns optimistic state, latest-wins concurrency, cancellation, stale-write
   fencing, and pending status. React composes `useOptimistic()`, `useFormStatus()`, and a Server
   Function.
5. eXact returns validated state effects or bounded refresh patches to precise consumers. The
   Next.js example revalidates its route, reruns affected Server Components, and merges their RSC
   payload.

Neither model sends database clients, credentials, or other server resources to the browser. In
eXact, `@exact shared` authorizes only the declared plain result contract; server context and task
authority remain server-owned.

`task.optimistic()` executes a synchronous state mutation as a generation-owned overlay. The
overlay is visible immediately and is removed automatically if that generation fails, is cancelled,
is superseded, or loses its component owner. A successful authoritative write replaces it. The
optimistic callback must be synchronous and is valid only for `latest()` or `queue()` task policy.

## JSX shorthand is finite

The compact JSX forms remove recurring mechanical code without creating a general directive
system. Intrinsic bindings support a fixed set of native property/event relationships and infer
conversion from the element and state type. Component bindings join two ordinary declared props,
such as `expanded:onExpandedChanged`. Write the full props and callback when an update validates,
transforms, rejects, logs, awaits, or returns a result.

Namespaced classes apply only to intrinsic elements. They cannot be combined with a
prop spread or duplicate a statically known token. JSX-producing array maps use stable identity
when an item key is declared or supplied; ordinary data transformations remain native
`Array.map()` calls.

A valueless namespaced class such as `className:counter` contributes its statically known token
unconditionally. Supplying a value, as in `className:is-even={condition}`, makes that contribution
conditional.

## Effects and tasks are different ownership choices

Use lifecycle registration for work whose lifetime is the mounted or active component instance.
Use a function task when work needs a name, inspectable status, direct invocation, cancellation,
concurrency policy, scheduling, Suspense readiness, optimistic state, or client/server placement.
Task functions expose compiler-synthetic status including `pending`, `result`, and `error` and own
each generation's signal, descendants, resources, and cleanup.

Authored task calls do not normally thread that signal themselves. The compiler injects or merges
it for recognized cancellable calls, including functions whose type exposes an `AbortSignal`
parameter or options field, fetches, and browser event listeners. Generated client/server
continuations also carry cancellation across their endpoint. An API that exposes no cancellable
contract can still have its stale state publication fenced, but its underlying operation cannot be
physically aborted.

Do not translate Hooks mechanically. Native eXact code should not add positional state, dependency
arrays, setter wrappers, reducer ceremony, or render-phase memoization to imitate React. Props stay
parent-owned; local mutable data belongs on `this.state`; derived values remain ordinary observed
expressions when possible.

## Migration boundary

Native conversion is not required for every React-owned component. The optional React
compatibility layer hosts supported React 18 and 19 components with React semantics inside an
explicit ownership boundary. Use that boundary for existing components and ecosystem packages;
use the patterns above for native eXact components.
