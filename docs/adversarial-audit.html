eXact Adversarial Codebase Audit

This document is intentionally skeptical. It focuses on release blockers, unstated assumptions, semantic mismatches, and places where the current implementation may let us believe the framework is more complete, secure, portable, or debuggable than it really is.

Audit date: 2026-07-11 Scope: packages, sample apps, docs, build scripts Verification observed: build, tests, package-content check passing before this audit Resolution pass: F-01, F-02, F-03, F-04, and F-07 resolved

Executive Summary

Strong foundation The repo now has meaningful package boundaries, a real compiler IR direction, server runtime validation, hydration tests, and clean package-content checks.
Main release risk Several features are correctly framed as "foundation", but the implementation can still be mistaken for a production distributed component protocol.
Highest priority fixes Remaining high-value work is source-map fidelity, public API boundaries, tarball smoke testing, and honest docs around partial compiler/runtime guarantees.
Biggest fallacy Passing runtime tests and package-content checks does not prove the compiler/server-component model is semantically complete.
Bottom line: eXact is not in a bad state. It is in a dangerous middle state: enough works that it feels real, but several core guarantees are still partial. That is exactly when a framework needs explicit guardrails, naming honesty, and adversarial tests.
Resolution note: a follow-up pass resolved the non-speculative implementation issues: generated IDs now use a longer digest with duplicate checks, .exact facade resolution handles JS and TS artifacts, exact state contracts support numeric array paths in hydrate/server validation, tests have a dedicated typecheck in release:check, and single-operation security hooks run once.

Detailed Findings

F-01: Stable IDs are only 32-bit hashes but act like protocol identity

Critical

stableId(...parts) uses a 32-bit FNV-style hash and returns a short base-36 string. These IDs are used for component IDs, action IDs, boundary IDs, render edges, element IDs, list IDs, and server manifest allowlists. That makes collision behavior a correctness and security concern, not just a cosmetic naming concern.

A collision inside serverActions can overwrite an entry before the runtime manifest ever sees it. A collision across manifests is detected only if the conflicting object metadata differs; a same-looking collision can remain invisible. Even non-malicious large projects eventually make 32-bit collisions plausible.

Recommendation: move to a longer deterministic digest, for example SHA-256 truncated to at least 96 or 128 bits, and add explicit duplicate-ID detection during compiler manifest creation before object insertion. Treat duplicate IDs as compiler errors.

Status: resolved with SHA-256 based IDs and duplicate checks for server actions, components, symbols, and boundaries.

Evidence: packages/compiler/src/ids.ts:1, packages/compiler/src/index.ts serverActions insertion, packages/server/src/manifest.ts conflict handling.

F-02: .exact facade resolution looks wrong for JSX artifacts

High

artifactPathsFor() emits .exact.client.js / .exact.server.js for .jsx inputs, but resolveExactArtifactImport() always resolves ./Component.exact to ./Component.exact.client.ts or ./Component.exact.server.ts. That means facade imports are probably broken for JSX source packages, despite docs presenting facade imports as build-tool agnostic.

Recommendation: make facade resolution extension-aware. Options: consult the artifact manifest, check for both .ts and .js, or encode the artifact extension in generated package exports instead of deriving blindly.

Status: resolved by checking existing .ts/.js artifacts and preferring the importer-appropriate extension when no file exists yet.

Evidence: packages/compiler/src/paths.ts:25, packages/compiler/src/artifacts.ts:93, Vite/Webpack/Bun adapters call the same resolver.

F-03: State contracts do not handle arrays consistently

High

Compiler state analysis can produce paths such as items.0 from array destructuring. The hydration client and server validation both walk state paths by requiring each intermediate value to be a plain object and rejecting arrays. This means a legitimate exact read from array state can be omitted by the client and rejected by the server.

This is a semantic mismatch between compiler contracts and protocol validation. It will be especially surprising because lists are a first-class framework story.

Recommendation: define path semantics explicitly. Either support arrays and numeric segments in both stateForContract() and stateMatchesContract(), or prevent the compiler from emitting exact numeric paths and mark them broad/unsupported instead.

Status: resolved by supporting numeric array segments in hydration state slicing and server state-contract validation, with tests on both sides.

Evidence: packages/compiler/src/state-analysis.ts array binding alias support, packages/hydrate/src/state.ts:16, packages/server/src/validation.ts:104.

F-04: Test files are no longer typechecked by the TypeScript build

High

Package tsconfig.json files now exclude *.test.ts and *.test.tsx so tests do not ship in build output. That is good for publishing, but it also means npm run build no longer typechecks test files. Vitest runs the tests, but it does not replace a TypeScript project typecheck for test-only imports, helper signatures, and expectation setup.

Recommendation: add a root tsconfig.test.json or package-level test configs with noEmit, then include it in release:check. Keep production builds clean, but typecheck tests separately.

Status: resolved with root tsconfig.test.json, typecheck:tests, and release:check.

Evidence: package tsconfig.json files exclude tests; package.json currently has build, test, and check:publish, but no test typecheck.

F-05: @exact/core exports too much as one public surface

High

The README already admits this, and the code confirms it: @exact/core exposes app-facing APIs beside framework internals such as component instance creation, rendering internals, vnode helpers, task observers, server boundary symbols, and error routing hooks.

Once external users import these internals, they become de facto API. This will make future refactors much more expensive.

Recommendation: split exports before public release. For example: @exact/core for app APIs, @exact/core/vnode for low-level vnode helpers, @exact/core/runtime for renderer/SSR internals, and possibly package-private imports for cross-package internals if the build allows it.

Evidence: packages/core/src/index.ts, README "next export cleanup" note.

F-06: Source maps are line-level approximations

Medium

The source-map implementation creates a generated-line to original-line mapping. It does not preserve columns, transformed node spans, names, or real TypeScript transform mapping. This is acceptable as an early debugging aid, but it should not be presented as full source-map support.

Recommendation: document current fidelity honestly and add tests around expected mapping behavior. Longer term, use TypeScript source-map output or a source-map builder that tracks generated node positions.

Evidence: packages/compiler/src/source-maps.ts:16, packages/compiler/src/index.ts:139.

F-07: Server security hooks run twice for single-operation requests

Medium

handleExactRequest() calls checkSecurityHooks() before dispatch. dispatchExactOperation() calls it again. For single requests, that means authorization and CSRF validation run twice. For batches, hooks run once for the batch and again per operation.

Double-running is not harmless if hooks consume one-time CSRF tokens, update audit records, refresh sessions, rate-limit, or perform expensive I/O.

Recommendation: make the policy explicit. Either run top-level hooks once and pass a verified context into dispatch, or intentionally support batch-level and operation-level hooks with separate hook names.

Status: resolved for single-operation requests; batches retain one top-level check plus per-operation dispatch checks.

Evidence: packages/server/src/index.ts:60, packages/server/src/index.ts:116, packages/server/src/index.ts:156.

F-08: State/context validation is not value-schema validation

Medium

The server validates that exact state paths exist and that submitted context tokens match the compiler contract. It does not validate the type, range, brand, tenant ownership, or semantic correctness of those values. That is a reasonable v1 boundary, but it is easy to mistake for full payload validation.

Recommendation: keep the manifest contract as the framework boundary, but expose an app-level schema hook per action or document that server actions must validate all business-critical values before using them.

Evidence: packages/server/src/validation.ts, especially stateMatchesContract() and contextMatchesContract().

F-09: SSR HTML diffing is intentionally narrow

Medium

diffBoundaryHtml() uses a small regex parser for framework-shaped HTML. That is defensible if the input is always eXact-generated boundary HTML, but it will not behave like a browser parser. It ignores comments, expects simple attributes, has limited style parsing, and falls back to replacement on many shape changes.

Recommendation: document this as "framework HTML diffing", not general HTML diffing. Add adversarial tests for comments, boolean attributes, single-quoted attributes, nested exact IDs, browser-normalized HTML, and malformed submitted boundary snapshots.

Evidence: packages/ssr/src/diff.ts:19, packages/ssr/src/diff.ts:211.

F-10: Initial streaming is root replacement, not granular async boundary streaming

Medium

The current document streaming path emits a shell, waits for observed tasks, then emits a root replacement if final HTML differs. This is useful, but it is not equivalent to granular server component streaming, Suspense-style boundary reveals, or progressive per-boundary hydration.

Recommendation: keep the current API, but name the limitation in docs and tests. Future work should stream boundary-level replacements keyed by compiler IDs instead of replacing the root document container.

Evidence: packages/ssr/src/index.ts:161, packages/ssr/src/index.ts:181, packages/ssr/src/index.ts:182.

F-11: Compiler split/capture inference is still easy to oversell

Medium

The compiler handles useful cases: event/ref islands, client component stubs, simple captures, derived consts, task placement, server-only imports, and JSON-safe boundary payloads. But this is not yet a general semantic JavaScript compiler. Closure capture, aliasing, dynamic property access, non-local side effects, namespace patterns, complex class/function boundaries, and expression-level distributed execution remain constrained.

Recommendation: keep adding focused compiler IR tests and diagnostics. When inference is uncertain, fail clearly or classify conservatively rather than silently producing an inefficient or incorrect split.

Evidence: packages/compiler/src/component-analysis.ts, packages/compiler/src/jsx-transform.ts, README "remaining work" and "expansion points" language.

F-12: npm package metadata is incomplete

Low

Public packages are missing description, license, and repository. This does not break code, but it is a release-quality issue and affects npm discoverability, legal clarity, and user trust.

Recommendation: add consistent metadata to all public packages before publishing. If the project is not ready to choose a license, it is not ready for public npm release.

Evidence: all package manifests under packages/*/package.json.

F-13: Package-content auditing is not install-from-tarball testing

Low

npm run check:publish is valuable: it catches source/tests/tsconfig/build-info leakage. It does not prove that packed tarballs install correctly in a clean external project, that exports resolve from Node and bundlers, or that transitive local file: dependencies become publishable version ranges.

Recommendation: add a smoke test that packs packages, installs them into a temporary outside-the-workspace app, imports each public entrypoint, runs exactc --help or a small transform, and builds a tiny DOM/SSR example.

Evidence: scripts/check-package-contents.mjs.

F-14: Local build outputs can remain stale

Low

During the audit, ignored dist/*.test.* outputs remained present locally after build hygiene changes. Package files exclusions now prevent them from shipping, but local stale output can still confuse debugging and manual inspection.

Recommendation: add a safe clean script for package dist directories and build-info files, then make release:check start from a clean build.

Evidence: package files exclusions were needed even after test build exclusions.

Fallacies To Avoid

  • "Tests pass, so the compiler is semantically complete." Current tests prove many important examples, not JavaScript semantic completeness.
  • "Manifest allowlisting means server actions are secure." Allowlisting prevents arbitrary dispatch; app data still needs authorization and schema validation.
  • "Source maps exist, so debugging is solved." Current maps are line-level approximations.
  • "Streaming exists, so server components are progressive." Initial streaming is currently shell plus root replacement.
  • "Package contents are clean, so packages are publish-ready." Metadata, dependency ranges, install-from-tarball tests, and API boundaries still matter.
  • "Generated IDs are stable, so they are safe protocol keys." Stability and collision resistance are different properties; the ID implementation has been strengthened, but this distinction remains worth remembering.

Recommended Fix Order

  1. Done: replace stableId() with a longer digest and add compiler duplicate-ID detection.
  2. Done: fix .exact facade resolution for JSX artifacts and add coverage for TS/JS artifact choices.
  3. Done: resolve array/numeric path semantics in state contracts and add hydrate/server validation tests.
  4. Done: add test typechecking through tsconfig.test.json or equivalent.
  5. Split public app APIs from framework internals in @exact/core.
  6. Add release:check that runs clean, build, test, test typecheck, package-content check, and tarball smoke tests.
  7. Reword docs where needed so current source maps, streaming, HTML diffing, and compiler inference are described as current capabilities, not completed end-state guarantees.
