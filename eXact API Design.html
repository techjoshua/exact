eXact

An extensible reactive web framework with explicit component state, durable component instances, standard JSX ergonomics, scoped context, typed refs, and lifecycle-managed tasks.

1. Philosophy

eXact is not intended to copy React's API surface. The goal is to support the same user-facing experiences while avoiding the accidental complexity introduced by render-time hooks, positional state slots, dependency arrays, and implicit component instances.

Explicit instance

Each component has a durable instance exposed as this. State, refs, tasks, lifecycle handlers, and diagnostics belong to that instance.

Render is repeatable

The component constructor runs once per instance and returns a render function. The render function can run many times.

Reactive by default

State, props, and context are reactive proxies. Reads during render become render dependencies. Writes schedule updates.

Extensible core

Plugins may decorate instances, augment TypeScript types, and subscribe to lifecycle events without bloating the framework core.

Design rule

Prefer fewer orthogonal primitives. Before adding a new API, ask whether it can be built from state, props, context, task, ref, render, lifecycle events, or plugins.

2. Component model

A component is a function called once per component instance. It initializes state, registers lifecycle handlers or tasks, and returns a render function. 

type CounterState = {
  count: number;
};

type CounterProps = {
  step?: number;
};

function Counter(
  this: Component<CounterState>,
  { step = 1 }: CounterProps
) {
  // Runs once per instance.
  this.state.count = 0;

  return () => {
    // Runs whenever render dependencies change.
    return (
      <button onClick={() => this.state.count += step}>
        Count: {this.state.count}
      </button>
    );
  };
}

Why this shape?

Constructor onceInitialization is normal code. There is no initState() ordering rule inside render and no hook-like slot order.
Render many timesThe returned function is the only repeated UI projection. Its reactive reads define what should rerender.
Props stay separateProps are external inputs from the parent. State is internal instance-owned data. Context is ambient capability/shared state.

Root rendering

import { render } from "@exact/dom";

render(<App />, document.getElementById("app")!);

3. Reactivity semantics

State, props, and context values are reactive proxies created to eXact's specification. The framework can detect both values and their underlying reactive references, while preserving natural authoring ergonomics as much as possible.

Render dependency tracking

During render, reactive reads are tracked automatically. When any tracked reference changes, the instance is scheduled for update. 

return () => (
  <section>
    <h1>{this.state.title}</h1>
    <p>Theme: {this.getContext(themeContext).name}</p>
  </section>
);

This render depends on state.title and themeContext.name. It does not depend on unrelated state or context fields.

Element-level dependency tracking

Generated JSX elements may capture their own reactive dependencies. Primitive state passed through JSX children or DOM props should be consumed by the generated element, not by the ancestor component render that created the element.

This prevents changes to child text, DOM props, or props.children payloads from forcing ancestor component rerenders when the ancestor structure itself has not changed.

State writes

State writes schedule UI updates, but they do not automatically become task dependencies. Writes are batched so multiple state mutations in the same turn produce one update. 

this.state.loading = true;
this.state.error = undefined;
this.state.options = [];
// One scheduled update, not three independent patches.

Reactive primitive wrappers

Reactive proxy fields may internally wrap primitives so framework APIs can distinguish a plain value from its reactive source reference.

For example, this.state.query may behave like a string while carrying internal metadata identifying state.query as a reactive reference. In control-flow comparisons, use loose equality such as state.mode == "compact" and state.mode != "full", or explicitly unwrap when strict primitive identity is required.

Caveat: primitive wrappers can create JavaScript edge cases around ===, typeof, and third-party library brand checks. Loose equality intentionally unwraps reactive primitives through JavaScript coercion, but strict equality cannot. Framework APIs should unwrap values automatically. Low-level unwrap/reference utilities should exist for plugins and advanced interop, but should not be part of the everyday component authoring path.

Framework-level reactive utilities

The runtime should expose low-level utilities for plugins and internal APIs, such as:

reactive.unwrap(value);        // get the plain value
reactive.ref(value);           // get the reactive reference, if present
reactive.isReactive(value);    // detect reactive wrappers/proxies
reactive.peek(fn);             // read without tracking
reactive.snapshot(value);      // produce debug/serialization snapshot

Average application developers should rarely need these directly. They exist so framework APIs like task, refs, devtools, SSR, hydration, and plugins can reason about reactive values correctly.

4. State, props, and context

State

State is typed through the component's this parameter and belongs to the durable component instance. 

type UserEditorState = {
  saving: boolean;
  draftName: string;
};

function UserEditor(this: Component<UserEditorState>, props: UserEditorProps) {
  this.state.saving = false;
  this.state.draftName = "";

  return () => <input value={this.state.draftName} />;
}

Props

Props are typed parameters. They are external, parent-owned, and reactive. Children are handled like React: props.children. 

type CardProps = {
  title: string;
  children?: JSX.Children;
};

function Card(this: Component<{}>, props: CardProps) {
  return () => (
    <section>
      <h2>{props.title}</h2>
      {props.children}
    </section>
  );
}

Context

Context is identified at runtime with typed symbols/tokens. This preserves TypeScript types while avoiding erased-generic ambiguity at runtime. 

type UserContextValue = {
  user: User;
  renameUser(name: string): Promise<void>;
};

export const userContext = createContext<UserContextValue>("user");
function UserProvider(this: Component<ProviderState>, props: Props) {
  this.setContext(userContext, {
    get user() {
      return this.state.user;
    },
    renameUser: async (name) => {
      this.state.user.name = name;
      await api.renameUser(this.state.user.id, name);
    }
  });

  return () => props.children;
}
function UserMenu(this: Component<{}>) {
  return () => {
    const { user, renameUser } = this.getContext(userContext);

    return <button onClick={() => renameUser("New name")}>{user.name}</button>;
  };
}

Context scoping: setContext creates a sub-context scope for descendants only. The provider component's own execution still uses its ancestor context. This is especially important for error handling fallback.

5. Tasks

this.task() is the lifecycle-managed work primitive. It handles async work, cleanup, cancellation, and dependency-triggered reruns.

Final task direction

Render dependencies are automatic. Task dependencies are explicit by passing dependency values before the task callback. The task callback receives unwrapped dependency values as positional parameters, followed by the task context. 

this.task(work);

Runs once and cleans up on unmount.

this.task(dep1, dep2, dep3, async (value1, value2, value3, { signal }) => {
  // reruns when dep1, dep2, or dep3 changes
});

Why explicit task dependencies?

Fully automatic task tracking creates feedback-loop hazards. A task often reads and writes related state fields. If reads inside the task body became dependencies, writes could restart the same task unnecessarily.

Avoided problem: An autocomplete task reads query, loading, or error, then writes loading, error, and options. If all task reads were auto-tracked, internal state updates could cause redundant or self-triggered reruns.

Task rules

  • this.task(work) runs once and is aborted/cleaned up on unmount.
  • this.task(dep1, dep2, ..., work) reruns when any dependency changes.
  • All previous task executions are aborted before rerun.
  • Cleanup functions are called before rerun and on unmount.
  • Task dependency values are unwrapped before being passed to the callback.
  • Task work is not dependency-tracked by default.
  • State writes inside task work schedule renders but do not themselves become task dependencies.

TypeScript shape

type TaskContext = {
  signal: AbortSignal;
};

type Cleanup = void | (() => void | Promise<void>);

type TaskResult = Cleanup | Promise<Cleanup>;

interface Component<State> {
  task(work: (ctx: TaskContext) => TaskResult): void;

  task<Deps extends readonly unknown[]>(
    ...args: [
      ...deps: Deps,
      work: (...args: [...values: Unwrapped<Deps>, ctx: TaskContext]) => TaskResult
    ]
  ): void;
}

Autocomplete task example

function Autocomplete<T>(
  this: Component<AutocompleteState<T>>,
  props: AutocompleteProps<T>
) {
  this.state.query = "";
  this.state.loading = false;
  this.state.options = [];
  this.state.error = undefined;

  this.task(
    this.state.query,
    props.search,
    async (query, search, { signal }) => {
      const trimmed = query.trim();

      if (!trimmed) {
        this.state.options = [];
        this.state.loading = false;
        this.state.error = undefined;
        return;
      }

      this.state.loading = true;
      this.state.error = undefined;

      await delay(200, signal); // debounce

      try {
        this.state.options = await search(trimmed, signal);
      } catch (err) {
        if (!signal.aborted) {
          this.state.error = "Could not load options";
        }
      } finally {
        if (!signal.aborted) {
          this.state.loading = false;
        }
      }
    }
  );

  return () => (
    <div class="autocomplete">
      <input
        value={this.state.query}
        placeholder={props.placeholder}
        onInput={e => this.state.query = e.currentTarget.value}
      />

      {this.state.loading && <div>Loading...</div>}
      {this.state.error && <div>{this.state.error}</div>}

      {!!this.state.options.length && (
        <ul>
          {this.map(
            this.state.options,
            props.getKey,
            option => (
              <li onClick={() => props.onSelect(option)}>
                {props.renderOption(option)}
              </li>
            )
          )}
        </ul>
      )}
    </div>
  );
}

Run-once task example

function Clock(this: Component<{ now: Date }>) {
  this.state.now = new Date();

  this.task(async ({ signal }) => {
    while (!signal.aborted) {
      await delay(1000, signal);
      this.state.now = new Date();
    }
  });

  return () => <time>{this.state.now.toLocaleTimeString()}</time>;
}

6. Events

Events use standard JSX props. No custom JSX transform is required beyond standard JSX-to-function-call translation. 

return () => (
  <button onClick={event => {
    // `this` is the component instance.
    this.state.count++;

    // DOM element is available through browser semantics.
    event.currentTarget.disabled = this.state.count > 10;
  }}>
    Increment
  </button>
);

Design decisions

  • Event handlers are stored by the runtime, typically through delegated listeners.
  • Handlers run with this bound to the component instance.
  • The DOM element remains available as event.currentTarget.
  • Event reads do not create render dependencies unless explicitly run inside a tracked context.
  • Inline lambdas are supported; the runtime updates handler metadata rather than attaching/removing native listeners constantly.

7. Refs

Refs are typed references to resources, not just DOM elements. They are symbol-backed keys with owner-bound bindings. 

export const inputRef = createRef<HTMLInputElement>("input");
export const editorRef = createRef<MonacoEditor>("editor");
function SearchBox(this: Component<SearchState>) {
  return () => <input ref={this.ref(inputRef)} />;
}
this.refs.get(inputRef)?.focus();

Forward-ref-like behavior

There is no special forwardRef. A parent can pass an owned ref binding through props. The child attaches it to a DOM node or resource. 

const searchInput = createRef<HTMLInputElement>("searchInput");

function Page(this: Component<PageState>) {
  return () => <SearchBox inputRef={this.ref(searchInput)} />;
}

function SearchBox(
  this: Component<SearchBoxState>,
  props: { inputRef?: RefBinding<HTMLInputElement> }
) {
  return () => <input ref={props.inputRef} />;
}

No expose()

The design avoids a separate imperative handle API. If a child owns a resource, it can fulfill a ref binding with that resource. The resource might be an element, Monaco editor instance, Leaflet map, WebGL context, video player, or anything else.

8. Lists and keys

eXact centralizes keyed list rendering with this.map(). JSX for each item does not specify a key; the framework returns a reactive fragment, derives keys from the collection-aware mapping call, and attaches them to generated children. 

{this.map(
  items,
  item => item.id,
  item => <li>{item.description}</li>
)}

Map signature

this.map() accepts the collection, a typed key generator, and a typed render lambda. The key generator must return the stable string identity for the item. 

this.map<T>(
  collection: Iterable<T>,
  key: (item: T) => string,
  render: (item: T) => JSX.Element
): JSX.Element;

Why keys live outside JSX

Keeping keys in this.map() makes keyed rendering explicit at the collection boundary and keeps item JSX focused on DOM/component props. The returned fragment owns the collection dependency, so structural add/remove/reorder updates can be reconciled without rerendering the parent component.

  • The key lambda receives a typed collection item and returns the durable domain identity.
  • The render lambda receives the same typed item and returns JSX without a key prop.
  • The runtime attaches keys to rendered children before reconciliation.
  • The list fragment, not the parent component render, owns structural collection invalidation.
  • Dev mode should warn for dynamic arrays rendered without stable identity.

Identity principle: keys are not a React-specific quirk. Any framework preserving component instances across reorder/insert/delete needs collection identity.

9. Lifecycle

Lifecycle handlers are instance event subscriptions registered during construction. They can have multiple subscribers. 

function Widget(this: Component<WidgetState>) {
  this.onMount(({ signal }) => {
    // component is mounted
  });

  this.onUnmount(({ reason }) => {
    // cleanup not already covered by tasks
  });

  return () => <div />;
}

Because component construction runs once, these are not hook-like. Registering lifecycle handlers during construction does not create render-time ordering rules.

Potential lifecycle events

Event Purpose Core?
onMount Instance enters mounted lifecycle. Yes
onUnmount Instance is removed; tasks are aborted and cleanup runs. Yes
onRender Instrumentation: render started/completed, duration, dependencies. Useful for plugins/devtools
onCommit After DOM patch commit; refs available. Possible, but avoid until use cases demand it

10. Error handling

Error handling can be modeled as a known context token exported by the framework or an error plugin. 

export const errorContext = createContext<ErrorReporter>("errors");

type ErrorReporter = {
  report(error: unknown, source: ErrorSource): void;
};
function ErrorBoundary(this: Component<{ error?: unknown }>, props: Props) {
  this.state.error = undefined;

  this.setContext(errorContext, {
    report: (error) => {
      this.state.error = error;
    }
  });

  return () => {
    if (this.state.error) {
      return <ErrorView error={this.state.error} />;
    }

    return props.children;
  };
}

Context fallback rule

setContext affects children only. Therefore an error handler provided by a component is itself executed under that component's ancestor context. If the handler throws, the runtime can naturally report that failure to the ancestor error context.

No special boundary type required: error boundaries fall out of scoped context plus runtime error reporting.

11. Plugins

Plugins are the main extension mechanism. They may augment component typing with new decorated instance methods and may subscribe to instance lifecycle events. 

type Plugin = {
  name: string;
  setup?(app: AppRuntime): void;
  createInstance?(instance: Component<any>): void;
};

Type augmentation

// @exact/logging

declare module "@exact/core" {
  interface Component<State> {
    log: Logger;
  }
}

Instance decoration and lifecycle subscription

export const performancePlugin: Plugin = {
  name: "performance",

  createInstance(instance) {
    const createdAt = performance.now();

    instance.onMount(() => {
      metrics.count(`${instance.type.name}.created`);
      metrics.timing(`${instance.type.name}.createMs`, performance.now() - createdAt);
    });

    instance.onRender(({ duration }) => {
      metrics.count(`${instance.type.name}.rendered`);
      metrics.timing(`${instance.type.name}.renderMs`, duration);
    });

    instance.onUnmount(() => {
      metrics.count(`${instance.type.name}.unmounted`);
    });
  }
};

Logging and debug as plugins/capabilities

log and debug should not be separate vertical systems baked into core.

  • this.log can be added by a logging plugin and routed through a logging context. Default behavior may write to console; apps may route by level/message to Datadog, server logs, or other sinks.
  • this.debug should be local-only: console/test output for developer introspection. It should not route through production logging infrastructure.
  • Debug can include state, props, context tokens, tasks, refs, dependency information, and instance identity. 
function SaveButton(this: Component<State>) {
  this.log.info("SaveButton created");

  this.debug("initial state");

  return () => <button>Save</button>;
}

Core policy: plugins may add helpers and subscribe to instance events, but should be built from core primitives rather than requiring special syntax.

12. SSR and hydration

The primitives do not create a major barrier to SSR, but SSR and hydration should be separate extensions to keep server-only and client-only logic out of each other's bundles.

Package split

// Server only
import { renderToString } from "@exact/ssr";

// Client only
import { hydrate } from "@exact/hydrate";
Package Responsibilities
@exact/ssr Server render, async constructor resolution, state capture, HTML markers, serialized payload generation.
@exact/hydrate Client reattachment, state restore, event binding, DOM reconciliation against existing HTML.

SSR behavior rules

  • Constructor may run on the server.
  • Render may run on the server.
  • Tasks, refs, browser events, and DOM lifecycle should be client-only by default unless explicitly marked server-safe.
  • State serialization should be controlled by SSR extension policy, not hardcoded into core. 
<div data-exact-id="UserEditor:42">...</div>
<script type="application/json" id="__EXACT_STATE__">
  { "42": { "draftName": "", "saving": false } }
</script>

13. Full example: autocomplete

type AutocompleteState<T> = {
  query: string;
  loading: boolean;
  options: T[];
  error?: string;
};

type AutocompleteProps<T> = {
  placeholder?: string;
  search(query: string, signal: AbortSignal): Promise<T[]>;
  getKey(option: T): string;
  renderOption(option: T): JSX.Element;
  onSelect(option: T): void;
};

function Autocomplete<T>(
  this: Component<AutocompleteState<T>>,
  props: AutocompleteProps<T>
) {
  this.state.query = "";
  this.state.loading = false;
  this.state.options = [];

  this.task(
    this.state.query,
    props.search,
    async (query, search, { signal }) => {
      const q = query.trim();

      if (!q) {
        this.state.options = [];
        this.state.loading = false;
        this.state.error = undefined;
        return;
      }

      this.state.loading = true;
      this.state.error = undefined;

      await delay(200, signal);

      try {
        this.state.options = await search(q, signal);
      } catch (err) {
        if (!signal.aborted) this.state.error = "Could not load options";
      } finally {
        if (!signal.aborted) this.state.loading = false;
      }
    }
  );

  return () => (
    <div class="autocomplete">
      <input
        value={this.state.query}
        placeholder={props.placeholder}
        onInput={event => {
          this.state.query = event.currentTarget.value;
        }}
      />

      {this.state.loading && <div class="status">Loading...</div>}
      {this.state.error && <div class="error">{this.state.error}</div>}

      <ul>
        {this.map(
          this.state.options,
          props.getKey,
          option => (
            <li onClick={() => props.onSelect(option)}>
              {props.renderOption(option)}
            </li>
          )
        )}
      </ul>
    </div>
  );
}

Why this is performant

  • Typing changes state.query, which schedules a render and restarts only the query-dependent task.
  • Previous debounce/fetch work is aborted.
  • State writes to loading, error, and options update the UI but do not restart the task.
  • Event delegation avoids listener churn.
  • Keyed list reconciliation preserves row identity.
  • DOM patching preserves focus and selection in the input.

15. Open questions and implementation-sensitive decisions

  1. Reactive primitive wrappers: Are wrapper semantics acceptable if reactive primitive comparisons intentionally use ==/!= or explicit unwrap rather than ===/!==?
  2. Task typing: How precise can variadic dependency typing be while keeping overloads understandable?
  3. Commit lifecycle: Is onCommit needed in core, or can refs/tasks cover the practical cases?
  4. Unkeyed arrays: How strongly should dev mode warn when plain Array.prototype.map produces dynamic children instead of this.map()?
  5. Hot reload: Constructor-once semantics require a deliberate HMR policy for preserving state while restarting tasks/lifecycle registrations.
  6. SSR serialization: Which state is serializable by default, and how does the SSR extension let apps opt in/out?
  7. React compatibility: A separate tree-shakable compatibility package can exist, but the core should not absorb React's hook semantics.

16. Current minimal core

The current proposed core API is intentionally small:

interface Component<State> {
  state: Reactive<State>;

  getContext<T>(token: ContextToken<T>): Reactive<T>;
  setContext<T>(token: ContextToken<T>, value: T): void;

  task(work: (ctx: TaskContext) => TaskResult): void;
  task<Deps extends readonly unknown[]>(
    ...args: [...deps: Deps, work: (...args: [...Unwrapped<Deps>, TaskContext]) => TaskResult]
  ): void;

  ref<T>(key: RefKey<T>): RefBinding<T>;
  refs: RefRegistry;

  map<T>(
    collection: Iterable<T>,
    key: (item: T) => string,
    render: (item: T) => JSX.Element
  ): JSX.Element;

  onMount(handler: LifecycleHandler): void;
  onUnmount(handler: LifecycleHandler): void;

  // Instrumentation/lifecycle events used by plugins/devtools.
  onRender?(handler: RenderEventHandler): void;
}

Core identity: eXact is an instance-oriented reactive component runtime where construction, rendering, and managed work are distinct phases. It preserves JSX ergonomics while avoiding hook ordering, dependency arrays, and hidden state slots.
